# 제품 품목·공정 흐름·공간 배치 통합 프론트 설계

- 기준일: 2026-10-02 (KST)
- 목표 화면: [통합 생산 워크스페이스](http://172.16.1.232/projects/P006/assets/equipment-registry/production-workspace-front.html?rev=asset-versions-20261002#product)
- 설계 원칙: 기존 6개 화면과 계획 schema를 확장하며 별도 HTML/iframe을 만들지 않는다.
- 상태: 프론트와 로그인 계정별 서버 계획 저장/복원 API 구현. 운영 승인 제품 자산 레지스트리 동기화 및 실제 로그인 계정 E2E는 별도 게이트.

## 1. 원씽과 성공 기준

제품 계획의 품목 ID가 BOM 여부와 무관하게 공정 입출력, 부산물, 운송, 생산 공간, 실행 3D까지 끊김 없이 이어져야 한다. BOM은 제품 구성만 나타내고, 중간품·부산물·공정 재공품 카탈로그와 역할을 분리한다. 각 품목은 공통 Asset Registry의 안정적인 자산 ID와 USD 경로·현재 카탈로그 지문을 보관하고, 브라우저 재생 가능한 GLB가 확인되면 같은 자산을 애니메이션에서 사용한다.

성공 기준 7개:

1. 품목은 `id`가 안정적으로 유지되고 `isBom`으로 제품 BOM 포함 여부를 분리하며 `kind`는 `원자재 | 부품 | 중간품 | 완제품 | 부산물` 중 하나다. 자산 연결은 `assetRef.assetId`로 고정하고 현재 카탈로그 지문과 USD 경로를 함께 저장한다.
2. 각 공정에 투입품, 산출품, 부산물을 연결하고 공정 단계 순서와 시간이 재생된다.
3. 각 이동에 운송 품목/수량, 출발·도착 부지/공장, 도착 공정, 운송 자산 후보가 저장된다.
4. 부지·공장·설비는 좌표계 기준 위치·방향·폭·깊이를 조절하고 실행 화면에 반영한다.
5. 3D 실행은 해당 공정 시점의 산출품을 발생 위치에 보여주며, 운송 중에는 선택 품목과 차량을 함께 이동한다.
6. 품목·공정·공간 참조를 삭제/변경할 때 잘못된 ID 연결을 경고하고 화면 도움말과 QA/다음 작업 문서를 동기화한다.
7. 모델 경로나 썸네일이 없으면 빈 상태를 명시하고 프록시 사용을 분명히 하며 실제 자산이라고 오인시키지 않는다.

8. 브라우저 초안과 로그인 계정 서버 계획을 구분한다. 서버 저장 후 재접속/다른 기기에서 같은 계정으로 목록·복원이 가능하고, 계획 전체를 한 문서(JSON)로 원자적 저장한다.
9. 계정 간 읽기·쓰기 범위를 해시 디렉터리로 격리하고, 동일 계획의 저장은 `baseVersion` 낙관적 잠금으로 제어해 충돌 시 최신 서버 문서를 자동 덮어쓰지 않는다.
10. 저장·복원에는 계획 ID, 버전, 수정 시각, 입력 크기 제한(2MiB), 액터 해시를 남기는 서버 이력을 둔다. 원본 대용량 USD/GLB는 계획 문서에 포함하지 않는다.

### 계획 서버 저장 계약

| 작업 | API | 요청/응답 | 권한·충돌 처리 |
|---|---|---|---|
| 계정 계획 목록 | `GET /projects/P006/registry-api/production-plans` | ID·이름·코드·계획 Revision·서버 version·수정 시각 | P006 로그인 필수, 로그인 accountId 별도 저장소 |
| 계획 복원 | `GET .../production-plans/{planId}` | 전체 계획 JSON + 서버 version | 다른 계정의 ID는 목록/복원 불가 |
| 신규/갱신 저장 | `POST .../production-plans/{planId}` | `{plan, baseVersion}`; 성공 `{version, updatedAt}` | CSRF 헤더·Origin 검사, 버전 불일치 409, 무단 덮어쓰기 금지 |
| 공통 자산 검색 | `GET /projects/P006/registry-api/assets?q={nameOrId}&limit=100` | `id`, 표시명, USD 경로, 이미지, 변형, `seed_hash`, 승인된 현재 `assetVersionId`, 버전 번호·파일 manifest·GLB 경로 | P006 로그인 필수. 승인 버전이 있으면 품목에 고정하고, 없으면 기존 자산 참조임을 표시 |
| 버전 목록 | `GET /projects/P006/registry-api/asset-versions/{assetId}` | 전체 버전·SHA-256 manifest·승인/현재 상태·작성/검토 이력 | 로그인 필수, 읽기 전용 |
| 새 버전 초안 | `POST .../asset-versions/{assetId}` | USD/GLB 서버 경로·변경 근거; 서버가 파일을 읽어 SHA-256과 크기 산출 | 프로젝트 관리자, 허용된 프로젝트 경로의 실제 파일만 등록 |
| 승인/반려 | `POST .../asset-versions/{assetId}/{versionId}/review` | `APPROVED` 또는 `REJECTED`와 검토 메모 | 프로젝트 관리자 + `RESULT_APPROVE`; 승인 직전 파일 hash 재검증 |
| 이전 버전 복원 | `POST .../asset-versions/{assetId}/{versionId}/restore` | 기존 승인 버전을 현재로 재지정 | 프로젝트 관리자 + `RESULT_APPROVE`; 이력은 보존하고 파일 hash가 일치해야 함 |
| 보존 | 서버 파일 저장 | 계획 최대 2MiB, 원자적 파일 교체, 별도 감사 JSONL | account ID는 SHA-256 디렉터리로 저장, 서버만 파일 접근 |

기존 브라우저 localStorage는 오프라인/임시 복구 초안으로 유지하고 서버 저장 성공을 뜻하지 않는다. `baseVersion=0`은 서버 신규 저장에만 사용하며 같은 ID가 있으면 충돌로 처리한다. 서버에서 계획을 열면 해당 버전을 로컬 상태에 고정하고, 이후 다른 계정 기기에서 먼저 저장했다면 409 안내 후 사용자가 최신본을 다시 열도록 한다. 계정 개인 계획이며 고객/조직 구성원 간 공유 권한은 아직 제공하지 않는다.

## 3. 데이터 계약 (프론트 초안)

```json
{
  "parts": [{
    "id": "stable-item-id",
    "code": "BODY-PANEL-01",
    "name": "차체 패널 성형품",
    "kind": "중간품",
    "isBom": false,
    "quantity": 1,
    "unit": "개",
    "model": "",
    "thumbnail": "",
    "assetRef": {
      "registry": "P006_SHARED_ASSET",
      "assetId": "N076",
      "catalogFingerprint": "seed_hash 값",
      "entryUsd": "/home/.../N076.usda",
      "webGlbPath": "/projects/P006/assets/3d-derived/N076.glb",
      "previewStatus": "READY"
    }
  }],
  "processes": [{
    "id": "process-id",
    "inputIds": [],
    "outputIds": [],
    "byproductIds": []
  }],
  "transports": [{
    "id": "transport-id",
    "itemId": "stable-item-id",
    "quantity": 1,
    "vehicleAssetId": null,
    "fromSiteId": "site-a",
    "toSiteId": "site-b",
    "toProcessId": "process-next"
  }]
}
```

`assetRef.catalogFingerprint`는 자산 행의 `seed_hash`이며 파일 hash가 아니다. 승인 버전이 존재하면 `assetVersionId`, `versionNumber`, SHA-256, 버전 상태와 웹 GLB 경로를 함께 고정한다. 이전 계획/버전 없는 자산은 `LEGACY_UNVERSIONED`로 보존한다. `previewStatus=READY`는 동일 ID의 웹 GLB 경로가 응답하고 브라우저에서 모델 로드를 시도할 수 있다는 뜻이다. GLB가 없으면 `USD_ONLY`로 저장하고 실행 시 기존 모델 또는 시연 프록시를 사용한다.

## 4. 배치 원칙

- `제품·부품`: BOM 표는 BOM 구성만 유지하고, 바로 이어지는 “생산 품목 카탈로그”에서 중간품/부산물/완제품도 한 화면에서 검색·추가·수정한다.
- `공정·운송`: 공정 카드 내부의 접힘 패널에서 투입/산출/부산물 체크를 하고, 같은 공정 간 이동은 운송 행으로 연결한다. 단순 공정 선택만으로 임의 자산을 강제 배정하지 않는다.
- `부지·공장·배치`: 기존 수치 입력을 유지하면서 빠른 X/Z/방향/폭/깊이 편집을 제공한다. 좌표는 가상 평면 기준이며, 위치 절대 기준과 단위(m)를 항상 표시한다.
- `실행·3D`: 기존 통합 실행 캔버스 안에서만 렌더링한다. 추가 iframe/외부 페이지는 사용하지 않는다. 전체/부지/공장/설비 카메라 기능과 실행시계를 보존한다.
- 미연결 데이터는 숨기지 않고 “자산 미연결/프록시 표시/근거 대기” 배지를 보여준다.

## 5. 프론트 대 서버 경계

현재 프론트가 책임지는 것: 입력·수정 UI, 브라우저 초안, JSON 입출력, 참조검사, 간단 좌표·거리·시간 표시, GLB/glTF 경로 미리보기, 절차 시연 애니메이션, 도움말/QA 현황.

운영 연결 전에 필요한 것: 실제 로그인 계정의 저장/복원 E2E, 조직 공유 승인, USD 변환 파이프라인, 차량 용량/경로·안전 제약, 실제 공정 근거와 실물 승인. 정식 자산 버전 원장은 추가됐으며 최초 로그인 계정의 생성·승인·복원 검수는 인증 세션 확보 후 실행한다.

API 비용은 이번 프론트 동작에서 발생하지 않는다. 배포는 정적 HTML 교체와 백업을 사용하며 런타임 서비스 재시작이 필요 없다.

## 7. 알려진 제한 및 다음 원씽

샘플 공정·품목은 화면 흐름 검증용 후보 데이터다. 생산기술 담당자의 공정 승인, 실제 중간재 형상, 부산물 처리 규칙, 운송차량 적합성은 확정하지 않는다. GLB 자산이 없으면 단순 프록시일 뿐이다.

**구현 추가:** 운송 건의 품목·차량 GLB·출발/도착·상차/이동/하차 시간을 공통 실행 시계에 연결하고, 명시한 도착 공정 시작을 운송 완료 뒤로 조정한다. 화면은 상차·이동·하차·도착 대기·다음 공정 투입 상태를 보여준다. 실제 실물 적재·차량 안전·운송 경로 검증은 범위 밖이다.

- 흐름 대조: 선형 연결은 직접 비교한다. 한 산출 품목이 여러 후행 공정으로 갈라지면 연결된 후행 투입 총량을 합산하고, 여러 선행 공정의 같은 품목 산출이 한 후행 공정으로 모이면 공급 총량을 합산한다. 분기와 합류가 겹쳐 경로별 배분 없이는 중복 계상될 수 있는 구조는 계산 대기로 남긴다. 같은 단위만 합산하며 변환표가 없으면 단위 불일치로 표시한다. 허용 오차 `max(1, |산출|, |투입|) × 1e-9` 이내는 일치, 산출 부족은 부족, 산출 초과는 잉여다.
- 의도적인 미지원 범위: 겹치는 분기·합류의 경로별 재고 배분, 수율/스크랩/불량/재작업, 포장/환산, 운송의 1회 적재량 대 총 필요량 해석, 차량 용량 단위, 실행 애니메이션 재고·생산량 변경. UI에 경계를 명시하고 계산을 가장하지 않는다.
- 화면: `공정·운송` 탭에서 수량 명세 다음에 `공정별 계획 소요량 · 흐름 검증`을 둔다. 계산표, 명시적 배치 수 입력, 선행 산출 ↔ 후행 투입의 일치/부족/잉여/단위불일치를 표시한다. 도움말은 배치 수와 미지원 항목을 같은 문구로 안내한다. JS 참조에 쿼리 버전을 붙여 브라우저 캐시된 이전 UI가 계속 보이는 문제를 방지한다.

## 21. 2026-10-04 운송 총량·차량 운행 횟수 계획 추정
- 업무 목적: 선택된 운송의 단일 품목 총수량과 차량 적재한도를 비교해 운행 횟수의 계획값을 먼저 검토한다.
- 입력: 운송 행의 품목 ID/기본 수량, 계획 전용 총수량 덮어쓰기, 확인된 단위중량(kg/품목단위), 차량별 적재 한도(kg), 차량 대수.
- 계산: 총중량 `Q × W`. 정수 개별품은 회차당 최대 적재 `floor(C / W)`, 최소 운행 `ceil(Q / 회차당 최대 적재)`로 계산해 개별품 초과 적재를 막는다. 소수 수량은 분할 단위로 취급해 `ceil(Q × W / C)` 하한을 계산한다. 차량 대수 기준 운영 회차는 `ceil(운행 횟수 / 차량 대수)`. 정수 수량은 회차별 균등 분배하되 포장·팔레트 제약은 판정하지 않는다.
- 차단 조건: 운송 품목 연결 누락, 양수가 아닌 수량/중량/적재량, 차량 미선택은 계산 불가로 표시한다. 데이터가 없다고 1개=1kg으로 가정하지 않는다.
- 보존/경계: 입력은 `frontPlanning.trips[transportId]` 계획 초안이며 기존 공정, 운송 시간, 등록 자산, 서버/API/DB, 실제 실행 3D에는 연결되지 않는다. 단일 품목의 총량 하한 추정이며, 혼적·상하차별 적재 상태·적재 안전·차량 경합을 검증했다고 주장하지 않는다.
- 회귀 검증 기준: 누락 중량 대기, 정확히 나누어 떨어지는 용량, 잔여 화물, 보유 차량 대수 반영, 소수 수량, 품목 ID 누락, 잘못된 입력 차단, 초안 복원, iframe 없는 렌더, JS 오류 0.
- 다음 바위: 검토된 품목 단위중량/포장 단위 및 다품목 상하차 자료로 모델을 보강한 뒤 실제 경로 시뮬레이션 연결을 설계한다.
