## 1. 설계 추적 범위

v9 원장에는 요구사항 115개, 원본 컨트롤 212개, 업무 시나리오 98개, 파생 테스트 996개가 있다. 원장의 115개 구현 상태는 전부 `NOT_VERIFIED`이며 완료로 간주할 수 없다. 프론트 구현은 아래 화면 동작을 제공할 뿐, 요구사항 수용 판정이나 운영 릴리스 증거를 자동으로 충족시키지 않는다.

## 2. 화면 및 데이터 흐름

`제품·부품 → 부지·공장·배치 → 공정·운송 → 설비 스튜디오 → 실행·3D → 검토·전체 업무`

6개 화면은 하나의 계획 객체를 공유한다. 브라우저 초안(localStorage)과 계정 서버 저장은 UI에서 분리하며, 서버 저장 후 로그인한 같은 계정으로 다른 기기에서 목록/복원한다. 설비 USD/GLB 참고자료는 계획 JSON과 별도로 계정 서버 자료 API에 보관한다. 고객/조직 공유와 실제 계정 다기기 브라우저 E2E는 미검증이다.

## 4. 자동 검사

`node --check workspace-front.js`와 생성 스크립트 구문검사를 수행한다. `node test-workspace-front.cjs`는 로컬 예시 데이터, 공정 그래프, 운송 시간, 공간 변환 및 잘못된 참조를 확인한다. `node qa-item-transport.cjs`는 실브라우저 익명 예시에서 6개 운송 시점과 iframe 미사용·JS 오류 여부를 검사한다. `py -3 test-asset-evidence-api.py`는 기존 서버 API 핸들러의 계정 범위 자료 등록·목록·다운로드를 확인한다. `py -3 test-production-plan-api.py`는 계획 생성/조회/갱신, 사용자 격리, stale-version 409, 크기·배열 제한을 확인한다. 자동 검사는 실제 브라우저에서 로그인한 사용자의 접근/권한 프로세스를 대신 검수하지 않는다.

## 5. 운영 릴리스 완료 전 필수 게이트

1. 기존 계획 API에서 계획·부지·공장·구역·셀·설비·공정·운송을 읽고 현재 schema와 호환 확인.
2. 실제 계정으로 서버 저장→로그아웃/다른 기기 로그인→계획 복원 흐름을 검수하고 조직 공유가 필요한지 결정.
3. 실제 사용자 역할(VIEWER/EDITOR/PROJECT_ADMIN 등)과 고객 경계 부정 접근 시험.
4. 제조사/모델 원장과 외부 변환을 연결하고, 현재 자산 버전의 승인 파일이 바뀌는 운영 알림을 추가. 참고자료 파일 API는 계정별 저장으로 부분 연결됨.
5. 운송 경로/차량 대기·반환과 품목 흐름에 대한 실제 데이터 기반 업무검증.
6. Kilo AI 5단계 작업 ID·이벤트 폴링/재접속 복원과 근거별 출처 검토를 구현한다. 자산 버전 저장·검토·승인은 이번 배포에 포함됨.
7. 제품·설비 USD의 실물 치수, 노드명·피벗·축·거리 확인 및 실제 애니메이션 검증.
8. 원장 115 요구사항과 98개 프로세스 시나리오를 입력/출력·액터·권한·API·DB·자동 QA에 연결하고 증거 첨부.
9. 전체/부지/공장/설비 선택, 변경/저장/새로고침, 녹화까지 운영 브라우저 시각·접근성 QA.

## 6. 구현 중 방지한 회귀

- 구역·셀 삭제 전 소속·공정·설비 참조를 검사한다.
- 셀 배정과 공정 담당 셀/설비 위치가 충돌하면 계획 검사에서 경고한다.
- 하위 공간 변환은 부지→공장→구역→셀 부모 회전을 포함한다.
- 실행의 하위 카메라 조작은 메인 카메라와 별도 상태로 보관한다.
- `showChanges=false`여도 제품 시연 형상 자체는 사라지지 않는다.
- iframe을 사용하지 않고 현재 문서 내에서 화면을 직접 렌더링한다.
