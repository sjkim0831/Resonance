# 내 업무 요약 화면 설계

## 1. 설계 상태

- 화면 ID: `emission-my-tasks`
- 경로: `/emission/my-tasks`
- 디자인 기준: KRDS Current
- 현재 실행 범위: `EMISSION` 탄소배출 프로젝트
- 실행 원장: `emission_project_task`
- 범위 판정: `DOMAIN_SCOPED`
- DB 변경: 없음
- DB 백업: 없음

> 이 화면은 16개 업무 종류 전체를 이미 통합한 화면이 아니다. 현재는 실제 실행 원장이 연결된 탄소배출 프로젝트 업무만 정확히 표시하며, 다른 업무 종류는 동일 계약으로 단계적으로 연결한다.

## 2. 육하원칙

| 구분 | 설계 |
|---|---|
| 누가 | 로그인 계정과 그 계정에 활성 배정된 액터 |
| 언제 | 업무 배정, 마감 임박, 선행 업무 완료, 보완 요청, 인계 발생 시 |
| 어디서 | GNB `내 업무 > 내 업무 요약` |
| 무엇을 | 현재 처리할 업무, 입력, 출력, 완료 조건, 다음 인계, 위험 |
| 어떻게 | 계정-액터-프로젝트 범위와 업무 상태를 서버에서 검증하고 실행 화면으로 이동 |
| 왜 | 사용자가 30초 안에 우선 업무를 찾고 다음 계정까지 끊김 없이 인계하기 위해 |

## 4. 정상 계정 릴레이

| 순서 | 업무 코드 | 계정 | 액터 | 허용 기능 | 대표 화면 |
|---:|---|---|---|---|---|
| 1 | `BASIC_INFO` | `qaowner26` | `COMPANY_MANAGER` | 범위 확정 | 프로젝트 상세 |
| 2 | `ACTIVITY_DATA` | `qadata26` | `SITE_DATA_OWNER` | 활동자료·증빙 제출 | 활동자료 입력 |
| 3 | `CALCULATION` | `qacalc26` | `CALCULATOR` | 배출량 산정 | 산정 화면 |
| 4 | `VERIFICATION` | `qaverify26` | `VERIFIER` | 독립 검증·보완 요청 | 검증 화면 |
| 5 | `APPROVAL` | `qaapprove26` | `APPROVER` | 승인·반려 | 승인 화면 |
| 6 | `REPORT` | `qaowner26` | `COMPANY_MANAGER` | 보고서 발행 | 보고서 제출 |
| 7 | `REGULATORY_SUBMISSION` | `qaowner26` | `COMPANY_MANAGER` | 규제 제출 패키지 생성·제출 | 규제 제출 |

계정은 테스트 fixture이며 실제 운영에서는 동일 액터 코드를 가진 프로젝트 범위 계정으로 치환한다.

## 5. 예외 릴레이

```text
VERIFICATION 부적합
  → CORRECTION_REQUIRED
  → qadata26 / SITE_DATA_OWNER / EMISSION_PROJECT_CORRECT
  → 자료 보완 + 변경 사유 + 증빙 + 재산정
  → qaverify26 / VERIFIER 재검증
  → 적합이면 APPROVAL, 재부적합이면 보완 분기 반복
```

`CORRECT`는 정상 경로의 고정 다섯 번째 업무가 아니라 검증 결과에 따라 열리는 조건부 예외 단계다.

## 6. 우선순위 표시 계약

화면의 우선순위는 공식 장애 등급 `P0/P1`이 아니다. 다음 서버 필드에서 계산한 화면 정렬용 운영 추정치다.

| 요소 | 원천 | 최대 점수 |
|---|---|---:|
| 마감 임박·지연 | `dueDate`, 서버 `serverDate` | 50 |
| 업무 중요도 | `priority` | 30 |
| 차단·예외 | `status`, `blockedReason` | 20 |

화면에는 점수와 함께 `정렬용 추정`을 표시한다. 데이터가 없으면 0으로 가정하지 않고 `근거 부족`으로 표시한다.

## 7. 권한 계약

업무는 다음 조건을 모두 만족할 때만 조회·시작할 수 있다.

1. 업무 `assignee_id`가 현재 계정과 일치한다.
2. 현재 계정의 활성 액터가 업무 `actor_code`와 정확히 일치한다.
3. 액터 배정의 프로젝트 또는 `*` 범위가 현재 프로젝트를 포함한다.
4. 데이터 범위가 `*`이거나 현재 프로젝트를 포함한다.
5. 모든 선행 업무가 완료됐다.
6. 관리자의 전체 조회는 명시적 서버 권한으로만 허용한다.

## 8. 화면 상태

- `LOADING`: 이전 데이터 대신 로딩 상태를 표시한다.
- `READY`: 8개 필수 섹션을 모두 표시한다.
- `EMPTY`: 업무가 없어도 8개 섹션과 다음 안내를 유지한다.
- `FORBIDDEN`: 잘못된 계정·액터의 시작 요청은 HTTP 403으로 차단한다.
- `ERROR`: JSON이 아닌 응답과 서버 오류를 오류 카드로 표시한다.
- `RECOVERY`: 새로고침 시 최신 권한·업무·인계 상태를 다시 읽는다.

빠른 필터 변경은 이전 요청을 취소해 오래된 응답이 최신 화면을 덮지 못하게 한다.

## 9. 지원면 동기화

| 지원면 | 기준 |
|---|---|
| 도움말 | 8개 `data-help-id`와 `helpContent.ts` |
| 화면 설계 | `pageManifests.ts`와 화면 계약 JSON |
| QA | `HAPPY_PATH`, `AUTHORITY`, `ISOLATION`, `EXCEPTION`, `RECOVERY` 정확 5종 |
| 업무 길잡이 | 현재 단계의 입력·출력·완료 조건·등록된 다음 단계 |
| 전체 업무 보기 | 전역 TaskQuest의 프로젝트·프로세스·단계 보기 |

## 10. 완료 판정

1. 정적 계약: 8섹션, 5 QA, 정상 7단계, 예외 보완 분기를 검증한다.
2. 권한 계약: 담당 계정은 시작 가능, 다른 액터 계정은 403이어야 한다.
3. API 계약: JSON 응답, 액터 범위, 서버 날짜, 알림을 확인한다.
4. DB 증거: 상태 전이 후 업무 원장을 재조회한다.
5. 브라우저: 데스크톱과 모바일에서 8섹션·표·진행률·전역 지원면을 확인한다.
6. 복구: 실패 시 업무 상태와 다음 인계가 중복 생성되지 않아야 한다.
