## 2. 적용 범위
| 원본 | 미러 |
|---|---|
| /opt/resonance-data/backups/postgres/base | /opt/resonance-data/backups/postgres/base-mirror |
| /opt/resonance-data/backups/postgres/primary | /opt/resonance-data/backups/postgres/mirror |

미러에 있는 파일과 원본의 동일 상대 경로를 비교했다. 미러에 없는 원본 전용 파일·다른 백업 경로·운영 DB 데이터는 건드리지 않았다.

## 3. 안전 설계
1. 경로가 심볼릭 링크를 통해 범위를 벗어나지 않는지 검사했다.
2. 동일 파일시스템·일반 파일·같은 크기·권한·소유권·확장 속성을 확인했다.
3. 열린 파일을 해시 검증 전후 조회하고 사용 중인 파일은 제외하도록 했다.
4. 양쪽 전체 내용을 SHA-256으로 읽어 비교했다. 검증 도중 inode·크기·수정시각·변경시각이 바뀌면 중단하도록 했다.
5. 원본·미러 경로, SHA-256, 권한, 소유권, 양쪽 원래 수정시각을 먼저 기록하고 fsync했다.
6. 임시 하드링크 생성 후 atomic replace로 미러 경로를 바꿨다.
7. 통합 파일을 다시 읽어 변경 전 SHA-256과 일치하는지 검증했다.

미러의 수정시각은 복사 때문에 일부 달랐다. 미러 원래 시각은 이력에 보존했고, 통합 후 두 경로는 원본 시각을 공유한다.

## 4. 운영·복구 주의
두 경로는 이제 독립 사본이 아니다. inode 손상·파일 직접 수정은 두 경로에 같이 영향을 준다. 백업을 직접 덮어쓰거나 rsync --inplace로 갱신하지 않는다. 새 백업은 고유 파일명 또는 임시 파일 작성 후 rename으로 게시한다. 복구·편집은 별도 독립 복사본에서 수행하고 inode가 원본과 다른지 확인한다. 기존 자동 백업 코드를 이번에 전수 개편한 것은 아니므로 재활성화 전 이 조건을 검토해야 한다.

하드링크 한 경로만 지우면 다른 경로의 내용은 남는다. 모든 링크를 지울 때 공간이 반환된다. 외부 디스크·원격 백업은 별도로 필요하다. 같은 /opt 볼륨의 두 사본은 원래도 디스크 전체 장애에 대한 독립 보호가 아니었다.

## 5. 검증 범위
통합 후 백엔드·네이티브 DB·프론트·P006 서비스 상태와 backend health, 홈 HTTP를 확인했다. 서비스 재시작·빌드·배포 없음. 화면·SDUI·DB 스키마·업무 가이드 수정 없음. 브라우저 시각 검수와 백업 전체 복원 테스트, 로그인/PDF 업무 E2E는 수행하지 않았다. 해시 일치는 기존 내용을 유지했다는 증거이며 백업의 논리적 복원 가능성을 새로 증명하는 것은 아니다.
