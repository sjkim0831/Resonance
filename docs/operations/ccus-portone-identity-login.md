# 포트원 통합인증 로그인 상세설계

## 최신 반영: 두 가지 로그인 진입 경로 (2026-09-06)
중요: 아래 기록의 독립 인증서 로그인/최초 계정 연결 계획은 아직 구현되지 않았다. 이번 변경은 통합인증 후 기존 비밀번호 로그인으로 이어지는 UI 연계이며, 인증서 단독 로그인이나 계정 영구 연결이 아니다.
1. 기존 로그인 버튼: 기존 아이디/비밀번호 로그인.
2. 통합인증 로그인 버튼: HTTPS 화면에서 아이디/비밀번호 입력 확인 → 포트원 인증창 → 서버 검증 성공 → 기존 submitLogin/actionLogin → 계정 상태/기존 MFA → 기존 세션 발급/화면 전환.
- HTTPS가 아니면 비밀번호/개인정보를 URL에 넣지 않고 HTTPS 로그인 화면으로 이동. 이동 후 입력을 다시 해야 한다.
- 비밀번호는 기존 로그인 API 외에 포트원/세션스토리지/로그에 저장 또는 전달하지 않음.
- 인증 실패/취소에는 로그인 API를 호출하지 않음. 인증 성공해도 비밀번호가 틀리면 로그인 안 됨.
- loginSuccess가 아닌 미지의 상태에는 로그인한 것처럼 화면을 전환하지 않도록 보완.
- 모의 브라우저 테스트 6건 PASS(약 5.75초): 인증+비밀번호 성공, 비밀번호 실패, MFA 필요, 제공자 검증 실패, 취소, 미지 로그인 상태. 실제 계정 로그인 E2E는 사용자 진행 대기.
- 시각 검수: portone-dual-login.png. PC 로그인 화면의 두 버튼 및 비밀번호 병행 안내 확인. 스크린샷의 fixture는 테스트용 가상 입력값.
- 모바일 redirect 복귀는 기존 테스트 검증 페이지를 사용하므로 자동 비밀번호 로그인 연결은 아직 미지원. 인증 복귀 후 기존 로그인 화면에서 로그인해야 함. 비밀번호를 모바일 복귀를 위해 저장하지 않음.
- 이번 변경은 추가 보안요소를 서버에서 강제하는 MFA 정책이 아니다. 기존 비밀번호 로그인은 별도로 유지되며 실제 인증과 로그인 계정이 동일인인지 영구 연결하는 기능은 없음.
- DB/Java 백엔드/권한 변경 및 서비스 재시작 없음.

## 최신 변경: 인증 결과 감사 로그 및 중복 인증서 버튼 정리
- 기존 성공 건은 화면 응답만 반환했고 서버에 인증 결과 이력을 저장하지 않았으므로 사후 로그 확인 불가. 사용자 제보와 코드의 성공 조건은 있으나 해당 건의 독립적인 서버 감사 증거는 없음.
- 2026-09-06 20:10 KST 이후 검증 완료 요청은 systemd journal의 [ccus-portone-audit] 이벤트로 기록. 시각, 해시 기반 확인번호, VERIFIED/FAILED, test 모드, 로그인 발급 false 및 제한된 실패 사유만 기록.
- CI 원문, 이름, 전화번호, 이메일, 비밀키, 쿠키, 원본 인증 ID는 감사 로그에 기록하지 않음. 로그 보존 기간은 기존 journal 정책을 따름.
- 성공/실패 알림에 확인번호 추가. 동일 번호로 서버 로그와 화면을 대조 가능. 과거 성공 로그를 소급 생성하지 않음.
- 실제 API 부정 테스트에서 존재하지 않는 인증 ID를 서버 조회하여 PROVIDER_HTTP_404 실패 감사 로그 생성 확인. 이 건은 자동 테스트이며 사용자 인증 실패 기록이 아님.
- 단위 테스트 11건, 실제 API 부정 테스트 6건, UI 테스트 7건 PASS. 초기 재시작 직후 API 연결 거절 1회 발생, 서버 준비 후 재실행 6건 PASS. 프록시 restart 명령 0.118초(준비 완료 시간과 다름).
- 로그인 화면의 공동인증서/금융인증서 별도 버튼 제거. 통합인증 이용 안내로 대체. 통합인증 로그인 버튼과 기존 비밀번호 로그인 유지. 스크린샷 portone-login-help.png.
- 실제 로그인 전환은 보류: 현 구성은 테스트 채널이며 운영 계정 연결 저장, 계정 소유권 재인증, 권한/MFA 검사, 세션 발급 통합이 미구현. 테스트 여부 문구만 지워 운영 로그인으로 처리하지 않음.

## 최신 변경: 통합인증 버튼 활성화 (2026-09-06)
이 항목이 아래의 준비 중/비활성화 기록보다 우선한다.
- 사용자 요청에 따라 기존 간편인증 버튼을 통합인증 로그인으로 교체. 별도 준비 중 중복 버튼 및 이전 KISA 간편인증 안내 제거. 공동/금융 인증서 등 나머지 버튼 유지.
- HTTPS 로그인: PortOne SDK → 서버 인증시도 발급 → 인증창 → 서버 완료 API → 결과 알림. 테스트 인증으로 로그인/계정 권한을 변경하지 않음.
- HTTP 로그인: Secure 쿠키 보호를 위해 HTTPS 검증 페이지를 팝업으로 연다. 새 창에서 동의 후 인증창 열기 필요. 팝업 차단시 사용자 안내.
- 신규 소스: projects/carbonet-frontend/source/src/features/public-entry/portoneLogin.ts. API 키는 브라우저에 포함하지 않음.
- 일반/관리자 국문/영문 4개 HTTP 경로의 실제 보안 팝업 열기 PASS. 자동 브라우저는 내부 인증서 신뢰 오류를 무시하는 테스트 옵션 사용(인증서 신뢰 검증 PASS를 의미하지 않음).
- SDK 및 완료 API를 모의 응답으로 대체한 UI 테스트 3건 PASS: 검증 성공 알림(로그인 아님), 실패 알림, 취소 알림. 취소시 완료 API 호출 없음.

## 1. 업무 및 액터
회원과 관리자 모두 동일 인증 흐름 사용. 서버가 로그인 계정을 확인하고 기존 계정 권한을 유지한다. 사용자가 계정 ID를 임의 입력하여 타 계정에 연결하는 기능은 제공하지 않는다.

## 2. 최초 연결
기존 아이디/비밀번호 로그인 및 필요한 MFA 완료 → 현재 로그인 계정 재확인 → 연결 동의 → 서버가 일회성 인증 시도 생성 → 포트원 통합인증 → 서버 결과 재조회 → CI 검증 → 현재 계정에만 연결.
연결 요청 시 계정 소유권 증명은 서버 세션을 사용한다. 시뮬레이터/위임 계정으로 연결 금지. 인증 시작 시점과 완료 시점의 실제 계정이 같아야 한다.

## 3. 이후 로그인
서버의 일회성 로그인 시도 생성 → 본인인증 → VERIFIED 및 동일 상점/채널 검증 → 검증된 CI의 고유 계정 매핑 조회 → 승인/잠금/탈퇴/사용중지 상태 검사 → 필요한 MFA 정책 적용 → 기존 세션 발급 → 계정 권한에 따른 메뉴.
CI 미제공/연결 없음/중복 연결이면 실패 처리. 이름, 이메일, 전화번호로 대체 검색하지 않는다.

## 4. 입력과 저장
- 필수 외부 검증 정보: 본인인증 ID, VERIFIED 상태, 검증된 CI, 인증 시각, 상점/채널 일치 근거.
- 서버 생성 정보: 만료 시간, 일회성 nonce, 브라우저 세션 바인딩, 목적 LINK 또는 LOGIN, 실제 계정 ID(연결 시).
- 이메일: 인증 요청/완료 조건/계정 연결 기준에서 제외. 기존 연락처 이메일, 이메일 비밀번호 복구, 가입 알림 기능은 별개이므로 삭제하지 않는다.
- DI: KG이니시스 통합인증에서 제공되지 않는 값이므로 필수로 요구하지 않는다. 임의 DI 생성 금지.
- CI: 로그/브라우저 응답에 원문 노출 금지. 별도 키를 이용한 HMAC 인덱스와 고유 제약으로 중복 연결 방지.
- 시크릿: 서버 비밀 설정 전용. 브라우저에는 storeId/channelKey/일회성 인증 ID만 제공.

## 5. 테스트/운영 경계
현재 설정은 테스트 채널이다. 테스트 결과는 실제 사용자 테이블의 인증 연결 정보나 로그인 토큰 저장소를 변경해서는 안 된다.
실연동 채널 설정과 검증이 완료되어야 실제 로그인 활성화가 가능하다. API Secret 인증 성공은 상점/채널의 실연동 본인인증 성공 증명이 아니다.

## 6. 코드 점검 결과
- MemberJoinIdentityOtpService에는 OTP 기반 자체 CI/DI 생성이 존재한다. 포트원 검증 CI와 혼용하지 않는다.
- ExternalAuthServiceImpl에는 요청 userId/userSe를 통해 인증 정보를 갱신하는 분기가 존재한다. 새로운 포트원 경로에서 재사용 금지.
- AuthTokenLoginServiceImpl은 토큰 발급 후 일부 회원 상태를 certified=false로만 표시한다. 새 로그인 경로에서는 토큰 발급 전에 계정 사용 가능 상태를 검증해야 한다.
- 현재 서버 비밀 파일은 root 600으로 애플리케이션 사용자 sjkim이 읽을 수 없다. 연동 배포 시 서비스 전용 credential 전달을 구성해야 하며 파일을 공개 권한으로 바꾸면 안 된다.

## 7. 필수 자동 시험
일반/관리자 정상 인증, 미연결 CI, 중복 CI, CI 누락, 취소, 만료, 재사용, 병렬 완료, 타 브라우저 완료, 타 계정 ID 주입, 인증 중 계정 전환, 테스트 결과 운영 연결 시도, 잠금/탈퇴/미승인 계정, 세션 발급 실패, MFA 필요 계정, 권한 없는 메뉴/API 차단, 모바일 redirect, 국문/영문.
결과 상태: 미실행. 실제 사용자 본인인증 및 로그인 E2E 미완료.

## 8. 안내 동기화
로그인: 통합인증 로그인 / 미연결 시 기존 계정으로 로그인하여 연결 안내.
계정 설정: 본인인증 연결 / 연결 시각 / 해제(재인증 필수).
QA: 테스트 인증과 운영 로그인 결과 별도 표시.
화면 설계 및 도움말: 이메일/DI 미요구, CI 미제공 시 지원 가능한 인증수단으로 재시도 안내.
